# TraitPilot 能力测试用例清单

> 本清单把 TraitPilot 当前**已落地**的各项能力逐条拆成可执行验证用例，用于回答「XX 功能到底怎么测它是否真具备」。
> 数据来源：`docs/harness-gap-analysis.md` 的实现盘点 + 仓库 `tests/` 实测。

## 怎么用这份清单

- **一行就是一条用例**：每一行的「怎么测」可直接复制执行；「预期可观察结果」是它该有的样子。
- **判据栏写的是「反例」**：请把它当**证伪条件**读——只有当你**没有**观察到反例里描述的现象时，才算「真具备」。任何一条反例命中，该能力即判**不具备（纸面具备）**。
- **三档验证力度**：① `pytest` 单测（快、离线、stub client 不发网络）→ ② `Playwright` E2E 脚本（需先起 Web）→ ③ **纯手工**（真模型 / curl 原始 SSE / 查磁盘真值）。清单里「自动化现状」列已标出每一条属于哪档，纯手工项是必须人工补的。
- **推荐节奏**：先跑全量 `pytest`（覆盖有自动化的一半），再跑 E2E 脚本，最后按表逐条补纯手工项。详见文末「推荐执行顺序」。
- **验证纪律**：凡承诺写入磁盘/执行副作用的用例，一律**查磁盘真值**（文件是否真消失/真出现、命令是否真跑），不要只信 `is_error`、提示文案或前端 DOM——那正是「纸面具备」的伪装。

### 弱判据（需加强后才可信）

- 「M3 死循环熔断」判据「最终文本含「熔断」」文案断言过脆：模型/实现改动可能换词，且无法区分「真熔断」与「恰好回了这个词」。应改判：stub 使动作持续重复后断言 client.calls 恰好停在 halt 阈值（不被 max_turns 兜底）、agent._guard_halted 为 True、且 tool_end 事件不再增加（后续工具被 agent.py:355 真正跳过）。
- 「M9 docker」自称「无 docker 时静默 return（假通过）」——这本身就是弱判据：绿灯不代表隔离成立。应改为 probe 失败时 pytest.skip 并显式打印原因，CI 里把该 skip 当可见信号，而非静默通过。
- 「M7 并行」用总耗时≈0.9s 作判据（时间阈值）是脆判据，受机器负载影响。应改：monkeypatch 让只读工具每次执行 sleep/touch 可观测标记并计数最大并发数，断言并发数>1 且结果按原 block 顺序对齐，而非测墙钟。
- 「幂等 reuse」判据留了「若模型只调用一次，此用例不成立」的退路——等于允许 happy path 假通过，依赖模型自觉重复调用。应改为直接对 ToolSet 连续两次 execute 相同 Bash 写命令，断言第二次命中复用（side-effect 只发生一次），不依赖模型行为。
- 「spill 落盘」判据「落盘内容完整」偏软：只查 meta.spilled 或「已转存」文案不够。应断言落盘文件尾行（如 seq 8000）真实存在，且随后用 Read 以 offset/limit 分段能取回被 MAX_OUTPUT 截断之外的部分。
- 「权限 deny 规则」判据用「返回含 rm -rf 且无输出」判断命令是否执行——输出为空也可能是命令执行了但无回显。应加副作用探针：命令若真跑会 touch 一个哨兵文件，断言哨兵文件未生成（查磁盘真值）。
- 「usage 累计」判据只点名 steps==0 或 output_tokens==7 单一字段即判假，判据不齐。应同时断言：steps 等于实际调用次数、output_tokens 等于各步真实和、latency_ms 单调递增（每步>0）、model 非空——任一不符才判假。
- 「归档」判据「默认列表不含」单一方向偏软：可能只是列表过滤。应三处磁盘真值同时断言：根目录 <sid>.jsonl 消失、archive/<sid>.jsonl 存在、/api/sessions?archived=1 含该 sid；缺一即判假（防「前端隐藏、磁盘没动」）。
- 「allowed-tools 收窄」判据自述有 hitless 歧义却未给最终判定，属于把结论留给读者。应明确断言收窄后 registry.schemas 的名称集合精确等于 (allowed∩已注册)∪{Skill,TaskOutput}，并对「allowed 名字全不在本套件」这一边界给出确定期望。
- 「cancel 取消」判据「client_calls>=1 即判假」把协作式语义当缺陷：cancel 只在 turn 边界生效，单次模型流内不打断是合法设计。判据应区分「cancel 后不再发起新的 create」（client.calls 不增长）与「当前流未被打断」（允许），否则会误伤正确实现。
- 「#14 cache_control」判据「不改消息内容」太笼统。应逐字节比较：开/关时 messages 与 system 文本完全相等，仅 system 末块与最后一个工具定义多出 cache_control 字段，且不是给每个工具都打（前缀稳定性）。
- 「Search 行号真实」判据只要求「行号非空且能读到关键字」偏软；应要求 start/end 与返回片段一致（打开该行核对包含 query 词、行号在文件行数范围内），并断言 hits 为空时工具不得报成功。
- 「默认关闭逐字节一致」多处用「与改造前一致」的定性说法，无基线快照，实为软判据。应为默认档生成请求体/后台 argv 的 golden 快照逐字节比对（如 sandbox host 的 kwargs、默认 tools 列表），而非靠人工判断「看起来没变」。
- 「TodoWrite 校验」判据「只回显原始 JSON 而无渲染 = 不具备」方向对，但「返回渲染文本+meta 进度」仍属软判据：未断言 meta 进度与实际输入条数一致，也未断言非法输入根本不进 history。应补：非法 JSON/多条 in_progress 时 history 不新增计划态、is_error=true。
- 「中断/异常收尾」判据「折叠用 display:none 时导出只剩前几行」依赖前端实现细节；应改为端到端导出断言（导出 Markdown 中含被折叠区域的全文文本、且中断后该段已落定不重复渲染），而非断言 CSS 属性选择器。
- 「M12 分层记忆 core 注入」判据「system prompt 里搜到该文本」偏软：应断言 core 出现在 system 字符串、且位置在稳定前缀内（不被 recall/动态块插入其前，以保 prompt cache 命中），并断言 core.md 文件确实落盘（非仅内存）。
- 「#12 重试语义」判据「401 也被反复重试即判假」正确，但缺「Retry-After 被尊重」的硬断言：应记录相邻两次尝试的时间间隔 ≥ 服务端 Retry-After 值，而非只断言「有延迟」。
